Think in first principles

Don't just copy what exists. Ask: "what is this thing really made of?" Break it down to the parts that are actually true, then rebuild from there.

The context window

The context window is just short-term memory

It's the AI's desk — everything it can see right now. Close the chat and the desk is wiped. So great builders give the AI three kinds of memory:

⚡

Short-term

working memory

The context window + a MEMORY.md sticky-note file: what we're doing right now.

📚

Long-term

curated

docs · wiki · specs — the stuff that stays true. You build this in Section 4.

🔎

Semantic

searchable

Past chats found by meaning: "what did we decide about X?"

Together they beat the blank-desk problem — the AI stops forgetting.

The 4th memory · live

And an MCP gives it live memory 🛰️

The three memories hold what we said and decided. An MCP covers what's true right now — it's a walkie-talkie between your AI and a live app.

Instead of you copy-pasting what's on screen, the AI reaches into the live app and reads it directly — the real, current state. That's how it stops guessing and starts seeing.

Short-term · long-term · semantic · live — that's the full memory picture.

03
Setup
Hands on. Get Cursor, GitHub, and Vercel running on your machine.
Setup · 1 of 3

🤖 Set up Cursor

  • 1.Update macOS first (Apple menu → System Settings → General → Software Update).
  • 2.Install Xcode Command Line Tools — this gives your Mac the developer basics (like Git).
  • 3.Download Cursor from cursor.com, drag it to Applications, open it, and sign in.
  • 4.Open a terminal inside Cursor: Terminal → New Terminal.
Run this in the terminal
# installs the Mac developer tools xcode-select --install # check it worked git --version

A window pops up — click Install and wait. When git --version prints a number, you're ready.

Setup · 2 of 3

🗂️ Set up GitHub

  • 1.Make a free account at github.com (pick a username you'd show a boss).
  • 2.Tell Git who you are (once per computer).
  • 3.Make your first project folder into a repo and take the first save.
  • 4.Create an empty repo on GitHub, then push your code up.
First save + push
git init git add . git commit -m "my first save" git branch -M main git remote add origin <your-repo-url> git push -u origin main

Commit early, commit often. Every commit is an undo point you can always return to.

Setup · 3 of 3

🚀 Set up Vercel

①

Sign up with GitHub

Go to vercel.com → Continue with GitHub. One click, no new password.

②

Import your repo

Add New → Project → pick the repo you just pushed. Vercel reads it automatically.

③

Deploy

Click Deploy, wait ~30 seconds, and you get a live link. 🎉

From now on, every time you git push, Vercel rebuilds and updates your live site. No extra steps.

🏎️

Your app is the race car. The harness is the safety gear + the pit crew around it — tests, memory, guardrails, a reviewer.

Without a harness, going fast means crashing. With one, you can let AI move fast and still stay safe. The next slides are your harness.

Set up your rig

Remember the three memories? This is the long-term one — a folder the AI reads before it works. Five kinds of notes:

Learned

Rule #1

A spec is a contract,
not vibes

Before the AI writes anything, write one clear paragraph: what are we building, and what does "done" look like?

Example spec

"A one-page site with my name, three things I like, and a button that changes the background color. Done = it loads on my phone, the button works, and it's live on Vercel."

If you can't say when it's done, neither can the AI.

Teach it from mistakes

The lesson habit

When something breaks, don't just fix it — write down the lesson so it never happens again.

Symptom

The button did nothing on my phone.

Root cause

I forgot to push before checking the live link.

Rule

Always git push, then test the live URL.

Add-only. Your list of lessons is how you (and the AI) get smarter over time.

The checker

Get a reviewer with teeth

🥷

Before you ship, have a second AI whose only job is to attack your change and try to find what's wrong.

✅

APPROVE

Nothing wrong found → ship it.

⛔

BLOCK

Here's the bug → fix, then re-check.

Rule: never approve out of politeness. The checker's whole value is being tough.

Prove it

Write the test — then try to break it

A test is a tiny robot that checks "does the important thing still work?" — automatically, every time. But a green check only counts if it could have gone red.

the tests

Next to your code

Files that live beside the thing they test. You write them as you build — not at the end.

the spec

What "done" means

Each thing the spec promises becomes a test. That's how you know you built what you said.

CI

The robot that won't forget

A checklist that runs every test on every push. It doesn't hold the tests — it just refuses to let you skip them.

🧪

Break your own code on purpose. Delete a line, run the test. If it still says PASS, you don't have a test — you have decoration. An AI will happily write one that's green no matter what.

All of this lives in your rules file — write the workflow down once, and the AI follows it every time without being asked.

Cursor best practices

Four habits that make AI actually good

  • 🎯Small asks. One change at a time beats "build my whole app." Easier to check, easier to fix.
  • 👀Read the diff before you save. See exactly what changed. Don't blind-accept.
  • 🧼Keep it simple. If the AI over-complicates, say "simpler." Simple code = fewer bugs.
  • 💾Commit when it works. A working version saved is a version you can always fall back to.
